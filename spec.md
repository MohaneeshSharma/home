## 1. Design System: UX4G

**Decision**: all UI is built from **UX4G Design System** components — the owner's explicit requirement, confirmed for this project.

- **Delivery method**: `ux4g-web-components` npm package (project is Next.js/Node per `intent.md` §4 — npm delivery, not CDN, per the UX4G contract's package-selection order). No mixing of npm and CDN delivery.
- **Strict implementation rule**: use UX4G's documented components, classes, variants, sizes, utilities, and semantic tokens wherever an equivalent exists. **Do not recreate a UX4G component with custom markup.** Custom CSS is allowed only for what UX4G genuinely doesn't provide (see §2, glassmorphism, and layout patterns like the bento grid) — kept minimal and documented inline with the reason.
- **Exact component-to-usage mapping (nav, buttons, cards, tabs, modal/dialog, forms, badges, avatar, timeline, accordion, etc.) is finalized during the Build stage**, once `ux4g-web-components`'s real docs/exports are inspected in the actual project — the UX4G skill contract explicitly forbids inventing component or token names ahead of that inspection, so this spec records *functional* needs, not literal API names:

| Functional need | Where used |
|---|---|
| Top nav + mobile nav | Site-wide header |
| Button (primary/secondary/ghost variants) | CTAs across Home, Work, Contact |
| Card | Project cards, blog cards, certificate cards, bento grid tiles |
| Tabs / segmented control | Work page category filter (UI/UX / Graphic Design / Video Editing / All, per `intent.md` §2) |
| Modal / Dialog | PDF viewer (certificates, resume), mobile menu |
| Form inputs (text, textarea, select) | Contact form, CMS admin forms |
| Badge / Tag | Project tags, blog tags, "Featured Case Study" labels |
| Avatar | About page, testimonials |
| Timeline | About page experience timeline |
| Rich text renderer | Blog post body (Tiptap output, see §6) |

### 1.1 Theme Tokens — Custom Brand Palette (confirmed, implemented)

The existing site's brand palette (`index.html`'s Tailwind config) is reused as the UX4G theme override, applied once at the application root per the UX4G token-override contract. **Resolved during Build** (`plan.md` §9 Phase 0): the installed `ux4g-web-components@2.1.0` package was inspected directly — its real primitive scale is `--ux4g-color-{role}-{50..950}` (not the placeholder `--ux4g-primary-*` shorthand guessed here in v1.0), defined once at `:root` and shared by both themes (dark mode remaps semantic tokens to different stops of the same scale, e.g. `primary-300` instead of `primary-600`). Dark mode itself is driven by `[data-theme="dark"]` on `<html>`, confirming the mechanism assumed in §3. Implemented in `styles/ux4g-theme.css`:

```css
:root {
  --ux4g-color-primary-600: #2563eb !important;  /* Royal Blue — primary */
  --ux4g-color-secondary-600: #9333ea !important; /* Purple — secondary accent */
  --ux4g-color-neutral-900: #0f172a !important;    /* Dark theme base surface */
  /* full 50–950 stops for primary/secondary also overridden — see the file */
}
```

UX4G's own semantic/status tokens (success/warning/error/info) are left at their defaults unless a specific need arises.

## 2. Visual Style: Glassmorphism

**Decision**: glassmorphism (frosted-glass, translucent surfaces) is the site's visual treatment, confirmed for this project — applied as a **surface-level decorative layer on top of UX4G**, not a replacement for UX4G's component structure. This is a deliberate reconciliation of two things in tension: UX4G is built for accessible, high-contrast, sober interfaces; glassmorphism (blur + transparency) can quietly erode contrast if applied carelessly. The rule that resolves it:

- Glass treatment (backdrop-blur + semi-transparent background + a subtle 1px border + soft shadow) is applied to **container/surface elements only**: the nav bar, hero cards, bento-grid tiles, stat badges, modals (PDF viewer, mobile menu drawer).
- **Text and interactive elements inside a glass surface must still meet WCAG AA contrast** (4.5:1 body text, 3:1 large text/UI controls) against the *effective* backdrop the blur produces — not just against the glass panel's nominal background color. This must be checked in both themes independently (§3), since the same opacity value produces different effective contrast against a light vs. dark backdrop.
- Interactive UX4G components (buttons, inputs, nav links) keep their own solid, UX4G-defined states (hover/focus/active/disabled) — glass is a background treatment behind them, not a restyle of the components themselves.
- Suggested (Build-stage to finalize) recipe: light theme glass = `background: rgba(255,255,255,0.7); backdrop-filter: blur(16px); border: 1px solid rgba(255,255,255,0.4)`; dark theme glass = `background: rgba(15,23,42,0.6); backdrop-filter: blur(16px); border: 1px solid rgba(255,255,255,0.08)` — both validated against real content contrast, not assumed.

## 3. Theming: Light + Dark (both required)

**Decision**: full light and dark theme support — not "dark mode as an afterthought." Every page and every component (UX4G's own components and the custom glass surfaces alike) must be checked in both themes before being considered done, per the UX4G contract's own completion-report requirement ("Light and dark theme checks").

- Theme switch persisted per-viewer (e.g. a `data-theme`/class toggle at the document root), default following system preference on first visit, with a manual toggle in the nav.
- §1.1's token overrides apply in both themes; UX4G's own dark-theme token set (if it ships one) is the base, with the brand overrides layered on top — exact mechanism confirmed during Build once the package is inspected.
- §2's two glass recipes (light/dark) are both required, not just the light one with a naive dark inversion.

## 4. Content Parity (reconfirmed from `brd.md` G5)

All content currently live on the static pages — Home hero/stats/expertise/selected-work copy, About's bio/timeline/testimonials, Project case studies, Blog posts, Certificates, Contact CTAs — **carries over as-is into the CMS as seed data.** Nothing is invented from scratch during the rebuild; the CMS is a new way to store and edit the same content, not a rewrite of it. Any content gaps (e.g. missing SEO fields, missing slugs) are filled in without changing the substance of the existing copy, unless the owner asks for a content revision separately.

## 5. About Page — Sourced from the CV

**Decision**: the About page's professional content (roles, dates, employers, skills, education) must be **reconciled against `Mohaneesh_UX_Designer.pdf`** — the resume is the source of truth for the owner's professional history, not whatever prose currently happens to be on `About.html`.

- **Build-stage task**: extract the CV's structured content (job titles, employers, dates, responsibilities, skills list, education) and use it to populate the About page's experience timeline and skills sections in the CMS.
- If `About.html`'s current copy and the CV disagree on any fact (a date, a title, a skill), **flag the mismatch to the owner rather than silently picking one** — this is a factual-accuracy issue, not a style choice.
- Once live, the About page's timeline becomes CMS-editable data (per `intent.md`'s Settings/CMS scope) — but its *initial* content is seeded from the CV, and any future CV updates should prompt a check for drift against the live About page.

## 6. Content & File Libraries (confirmed choices)

| Need | Library | Notes |
|---|---|---|
| **PDF viewing** (certificate PDFs, resume) | **pdf.js** (`pdfjs-dist`, Mozilla's official package) | Replaces today's native `<embed>`/browser-plugin `openModal()` pattern. Renders pages to canvas inside a UX4G Modal/Dialog + glass surface — a native browser PDF plugin can't be restyled to match the design system/glass theme, a canvas-rendered pdf.js viewer can. |
| **Blog rich-text editing** (CMS) | **Tiptap** | Already recommended in `intent.md` v2.0 §4; now a locked spec decision. Produces structured, sanitizable output — replaces the current raw-HTML-paste `content` field pattern. Output is sanitized server-side before storage/render regardless of Tiptap's own escaping (defense in depth, per `gaurdrail.md`'s security guardrails). |

## 7. Interaction & State Design (expert UX baseline)

Every screen in §1's component list is designed with all of its real states, not just its "happy path" — this is what separates a merely functional UI from an expert one, and it is now enforced as a React-level rule too (`plan.md` §3.1, `gaurdrail.md` §3):

- **Loading**: skeleton/placeholder states for Work/Blogs/Certificates grids and the CMS dashboard — never a blank screen or layout jump when content resolves.
- **Empty**: a designed empty state for "no projects in this category yet," "no leads yet," etc. — not just an empty `<div>`.
- **Error**: a designed error state for failed data loads and failed form submissions (contact form, CMS forms) — with a clear recovery action, not a silent failure or a raw error string.
- **Interactive feedback**: every button/link has visible hover, focus, active, and disabled states from UX4G's own component states (§1) — glass surfaces (§2) never replace these, only sit behind them.
- **Motion with purpose**: consistent with `brd.md` §4's "purposeful motion" quality-bar trait — reveals, transitions, and the PDF-modal open/close all use motion to clarify what changed, not as decoration.
