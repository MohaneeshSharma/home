# Implementation Plan
## Mohaneesh Sharma Portfolio — Dynamic Multi-Discipline Rebuild

Version: 2.0 — full rewrite, replaces v1.0's static `vite-react-ssg` plan
Companion to: `intent.md`, `brd.md`, `spec.md`, `gaurdrail.md`
SDLC stage: **Build** — this artifact is generated by reading `intent.md` (Plan), `brd.md`/`spec.md` (Design), and turns them into the concrete technical plan the diff+tests will implement against.

**What changed from v1.0**: v1.0 planned a static Vite + `vite-react-ssg` site. `intent.md` v2.0–v3.0 and `brd.md` v2.0 confirmed a real **dynamic, database-backed** application with a CMS+CRM. `spec.md` v1.0 then locked in the UX4G design system, glassmorphism, mandatory light/dark theming, and specific libraries (pdf.js, Tiptap). This version replaces the entire tech-stack/rendering section and adds a React code-quality bar (§3) so the Build stage has an explicit standard to write against, not just a stack list.

## 3. React Code Quality Bar (Build-stage standard)

Every component in this codebase is held to the **Impeccable React** contract — "code a senior reviewer would merge without comments," not just "it renders." This is now a Build-stage acceptance gate alongside `gaurdrail.md`'s other rules.

### 3.1 Component contract (all five, every component)
1. One reason to exist — no `ProjectCardAndFetcher`-style components.
2. Props are the full API — no reaching into globals, no `any`.
3. Renders are pure — no mutation during render, no non-deterministic output.
4. Every state (loading/empty/error/partial) is designed, not an afterthought — this directly extends `spec.md`'s "every state has a rendered representation" requirement into a code rule.
5. Operable by keyboard — every clickable thing is focusable with an accessible name (ties directly into `gaurdrail.md` §8 accessibility guardrails).

### 3.2 State placement (decide before coding — stop at first match)

| Value | Belongs in |
|---|---|
| Computable from existing props/state | Nothing — derive inline |
| Read by one component only | local `useState` |
| Shared by a few siblings | `useState` in closest common parent |
| Server data (projects, blogs, certificates, leads) | **Data fetched via Server Components / route handlers, not `useEffect` + `useState`** |
| Belongs in the URL (Work page category filter, blog search) | Router search params |
| App-wide, rarely changes (theme = light/dark) | Context |
| App-wide, high-frequency | Not expected to be needed at this scale — flag before adding a store |

This directly resolves a concrete decision the Work page needs: the **category filter tabs** (`intent.md` §2.4) read/write a URL search param (`?category=video_editing`), not local component state — so the filter is shareable/bookmarkable and survives refresh.

### 3.3 Effects — the shrinking list
`useEffect` is only for synchronizing with something outside React: the Tiptap editor instance lifecycle, pdf.js canvas rendering/cleanup, focus management in the PDF/mobile-menu modals, analytics. **Not** for fetching CMS data (use Server Components/route handlers), deriving values, or resetting state on prop change (use a `key`).

### 3.4 React 19 idioms (used throughout)
- **Contact form + every CMS admin form** → `<form action={fn}>` with `useActionState` for pending/error state (directly replaces `admin.html`'s old manual-state pattern) and `useFormStatus` in submit buttons.
- **Lead status updates in the CRM (new/contacted/closed)** → `useOptimistic` for instant UI feedback.
- **Refs** → plain `ref` prop, no `forwardRef`.
- **Server data in Client Components** → `use()` inside `<Suspense>` where a Server Component boundary isn't the natural fit.
- Memoization only where the (opt-in) React Compiler isn't handling it, and only where measured.

### 3.5 TypeScript
- Every content type modeled as a discriminated union where states are mutually exclusive (loading/error/ready), and `Project.category` is a literal union (`'ui_ux' | 'graphic_design' | 'video_editing'`, per `intent.md` §5) — not a loose `string`.
- No `any`, no silencing `as`. Props typed and exported for shared components.

### 3.6 Anti-patterns explicitly banned in this codebase
Straight from the skill's rejection list, called out here because this project has concrete places they'd otherwise creep in:
- `useEffect`+`setState` to mirror CMS data → use Server Components.
- `key={index}` on Project/Blog/Certificate lists (these lists reorder via `display_order`/filters) → use the record's real `id`.
- `dangerouslySetInnerHTML` on Tiptap blog content → sanitize server-side first (`lib/sanitize.ts`), per `gaurdrail.md` §5.
- One `useState` per field on the (multi-field) Project/Blog admin forms → `useActionState`/`useReducer`, not a pile of individual states.

### 3.7 Pre-delivery review gate
Before any component work is considered done: no misplaced `useEffect`, no `any`/unexplained `as`, all states rendered deliberately, stable list keys, full keyboard operability, no leftover `console.log`/TODO, cancellable async work, StrictMode-safe. Multi-file changes get actually run (typecheck/build/render), not just asserted correct.

## 7. Media & Content Handling

- Images: Supabase Storage, served via Next.js `<Image>` for optimization/lazy-loading.
- Video: embed-only (YouTube unlisted/Vimeo), per `intent.md` §2.3 — no raw video upload pipeline is built.
- Blog content: authored in Tiptap, stored as sanitized JSON/HTML, rendered through a controlled renderer (no raw `dangerouslySetInnerHTML` on unsanitized input).
- PDFs: uploaded to Supabase Storage, rendered client-side via pdf.js inside `<PdfViewerModal>`.

## 8. SEO Implementation

- Next.js `generateMetadata` per route: unique title/description/canonical (`www.mohaneesh.com`)/OG/Twitter Card.
- JSON-LD: `Person` (Home/About), `CreativeWork` (Work case studies), `BlogPosting` (blog posts) — injected via the route's metadata/server output, not client-side.
- `sitemap.xml`/`robots.txt` generated from the real route list (Next.js's built-in `sitemap.ts`/`robots.ts`), including dynamic `/work/[slug]` and `/blogs/[slug]` entries pulled from the database at build/request time.
- Republished Medium/LinkedIn posts get `rel=canonical` pointing at the on-site version plus the visible attribution link (`brd.md` FR13).

## 9. Migration Phases

1. **Phase 0 — Foundation**: Next.js + TypeScript scaffold, Supabase project (DB schema from §4, Auth, Storage buckets), `ux4g-web-components` installed and inspected (resolve the exact component/token names flagged as open in `spec.md`), theme tokens wired (`spec.md` §1.1), glass CSS primitives (`spec.md` §2) built and contrast-checked in both themes.
2. **Phase 1 — Shared shell**: `<Header>`, `<MobileNav>`, `<Footer>`, `<SEO>`, base layout/routing; Home + About rendering against real (seeded) data.
3. **Phase 2 — Content-driven pages**: Work (category-filtered), Blogs, Certificates against the real schema; `<PdfViewerModal>` (pdf.js) and blog rendering pipeline (sanitized Tiptap output) built.
4. **Phase 3 — CMS + CRM**: `/admin` — authenticated Projects/Blogs/Certificates CRUD (`useActionState` forms, Tiptap editor), Leads module, Contact form wired to it.
5. **Phase 4 — Content migration**: seed real content from the current static pages (`spec.md` §4) and the CV (`spec.md` §5); migrate the owner-selected Medium/LinkedIn posts (`brd.md` §9.1) with attribution/canonical setup.
6. **Phase 5 — SEO + performance + design QA**: metadata/JSON-LD/sitemap pass; Lighthouse targets (`gaurdrail.md` §4/§7); light+dark theme check and glass-surface contrast check on every page (`spec.md` §2–3); React Impeccable pre-delivery gate (§3.7) run across all components.
7. **Phase 6 — Deploy**: Vercel + Supabase production, `www.mohaneesh.com` DNS/CNAME cutover, old-domain redirect decision (`intent.md` §4) executed.

- Auth check: admin routes unreachable without a valid Supabase session; write API routes reject unauthenticated requests.
- Keyboard-only pass through nav, Work filter tabs, PDF modal, contact form, and every CMS admin form.
