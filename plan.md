## 3. React Code Quality Bar (Build-stage standard)

Every component in this codebase is held to the **Impeccable React** contract — "code a senior reviewer would merge without comments," not just "it renders." This is now a Build-stage acceptance gate alongside `gaurdrail.md`'s other rules.

### 3.1 Component contract (all five, every component)
1. One reason to exist — no `ProjectCardAndFetcher`-style components.
2. Props are the full API — no reaching into globals, no `any`.
3. Renders are pure — no mutation during render, no non-deterministic output.
4. Every state (loading/empty/error/partial) is designed, not an afterthought.
5. Operable by keyboard — every clickable thing is focusable with an accessible name.

### 3.2 State placement (decide before coding — stop at first match)

| Value | Belongs in |
|---|---|
| Computable from existing props/state | Nothing — derive inline |
| Read by one component only | local `useState` |
| Shared by a few siblings | `useState` in closest common parent |
| Server data (projects, blogs, certificates, leads) | **Data fetched via Server Components / route handlers, not `useEffect` + `useState`** |
| Belongs in the URL (Work page category filter, blog search) | Router search params |
| App-wide, rarely changes (theme = light/dark, admin session) | Context |
| App-wide, high-frequency | Not expected to be needed at this scale — flag before adding a store |

The Work page's **category filter tabs** (`intent.md` §2.4) read/write a URL search param (`?category=video_editing`), not local component state.

### 3.3 Effects — the shrinking list
`useEffect` is only for synchronizing with something outside React: the Tiptap editor instance lifecycle, pdf.js canvas rendering/cleanup, focus management in the PDF/mobile-menu modals, analytics. **Not** for fetching CMS data (use Server Components/route handlers), deriving values, or resetting state on prop change (use a `key`).

### 3.4 React 19 idioms (used throughout)
- **Contact form + every CMS admin form** → `<form action={fn}>` with `useActionState` for pending/error state and `useFormStatus` in submit buttons.
- **Lead status updates in the CRM (new/contacted/closed)** → `useOptimistic` for instant UI feedback.
- **Refs** → plain `ref` prop, no `forwardRef`.
- **Server data in Client Components** → `use()` inside `<Suspense>` where a Server Component boundary isn't the natural fit.
- Memoization only where the (opt-in) React Compiler isn't handling it, and only where measured.

### 3.5 TypeScript
- Every content type modeled as a discriminated union where states are mutually exclusive (loading/error/ready), and `Project.category` is a literal union (`'ui_ux' | 'graphic_design' | 'video_editing'`) — not a loose `string`.
- Mongoose schemas paired with TypeScript interfaces (via `mongoose.InferSchemaType` or explicit interfaces) so documents coming out of the DB are typed, not `any`.
- No `any`, no silencing `as`. Props typed and exported for shared components.

### 3.6 Anti-patterns explicitly banned in this codebase
- `useEffect`+`setState` to mirror CMS data → use Server Components.
- `key={index}` on Project/Blog/Certificate lists (these lists reorder via `display_order`/filters) → use the record's real `_id`.
- `dangerouslySetInnerHTML` on Tiptap blog content → sanitize server-side first (`lib/sanitize.ts`), per `gaurdrail.md` §6.
- One `useState` per field on the (multi-field) Project/Blog admin forms → `useActionState`/`useReducer`, not a pile of individual states.

### 3.7 Pre-delivery review gate
Before any component work is considered done: no misplaced `useEffect`, no `any`/unexplained `as`, all states rendered deliberately, stable list keys, full keyboard operability, no leftover `console.log`/TODO, cancellable async work, StrictMode-safe. Multi-file changes get actually run (typecheck/build/render), not just asserted correct.

## 7. Media & Content Handling

- Images: saved to local `/uploads`, served via Next.js `<Image>` for optimization/lazy-loading (works with a local file path source just as well as a remote one).
- Video: embed-only (YouTube unlisted/Vimeo), per `intent.md` §2.3 — no raw video upload pipeline is built, local disk or otherwise.
- Blog content: authored in Tiptap, stored as sanitized JSON/HTML in MongoDB, rendered through a controlled renderer (no raw `dangerouslySetInnerHTML` on unsanitized input).
- PDFs: saved to local `/uploads`, rendered client-side via pdf.js inside `<PdfViewerModal>`.
- `/uploads` is gitignored — it's local runtime state, not source; moving to a hosted phase later will need a real migration of these files to whatever storage is chosen then (flagged, not solved, now).

## 10. Local Development Setup

**Environment**: the owner develops on their own Windows machine, with the repo cloned at a path like `D:\2026\mohaneesh.com\home` — not inside a cloud session. `lib/db.ts`, `.env.local.example`, and this section are written for that machine.

### Windows: MongoDB inside the project folder (no system-wide install, no Docker)

MongoDB's own Windows service installer (the MSI) installs system-wide and runs as a background Windows Service. Since the ask is to keep MongoDB local to the project folder instead, use the **portable ZIP build** and point it at a data folder inside the repo:

1. Download **MongoDB Community Server** for Windows as the **ZIP** package (not the MSI) from `https://www.mongodb.com/try/download/community` — select Platform: Windows, Package: `zip`.
2. Extract it into the project folder, e.g. `D:\2026\mohaneesh.com\home\mongodb\` (so `mongod.exe` ends up at `D:\2026\mohaneesh.com\home\mongodb\bin\mongod.exe`).
3. Create a data folder next to it: `D:\2026\mohaneesh.com\home\mongodb-data\`.
4. Both `mongodb\` and `mongodb-data\` are already covered by `.gitignore` — they're machine-local runtime state, never committed.
5. Start it (from a terminal, each time you want the DB running — this ZIP build isn't installed as an auto-starting service):
   ```
   D:\2026\mohaneesh.com\home\mongodb\bin\mongod.exe --dbpath "D:\2026\mohaneesh.com\home\mongodb-data" --port 27017 --bind_ip 127.0.0.1
   ```
   `--bind_ip 127.0.0.1` keeps it unreachable from outside the machine, per `gaurdrail.md` §6. Leave this terminal window running while developing; `Ctrl+C` to stop it.
6. `MONGODB_URI=mongodb://127.0.0.1:27017/portfolio` in `.env.local` (already the default in `.env.local.example`) then just works — no path changes needed, since `mongod` listens on the same `localhost:27017` regardless of where its files live on disk.

### Windows: auto-starting alternative — install as a Windows Service

If starting `mongod.exe` manually every session is annoying, register it as a Windows Service instead — same portable ZIP, same project-folder data path, but Windows starts it automatically at boot rather than needing a terminal window kept open.

1. Copy `mongod.cfg.example` (repo root) to `mongod.cfg` — already gitignored; edit the two paths inside only if your clone isn't at `D:\2026\mohaneesh.com\home`.
2. Create the log folder: `D:\2026\mohaneesh.com\home\mongodb-logs\` (also gitignored).
3. Open **Command Prompt as Administrator** (service install/start requires elevation), then:
   ```
   cd D:\2026\mohaneesh.com\home\mongodb\bin
   mongod.exe --config "D:\2026\mohaneesh.com\home\mongod.cfg" --install --serviceName "PortfolioMongoDB" --serviceDisplayName "Portfolio MongoDB (local dev)"
   ```
   A custom `--serviceName` avoids clashing with any other "MongoDB" service already on the machine from a prior install.
4. Start it: `net start PortfolioMongoDB` (and `net stop PortfolioMongoDB` to stop). `mongod --install` registers the service as Automatic-start by default — confirm with `sc qc PortfolioMongoDB` (look for `START_TYPE : AUTO_START`), or force it with `sc config PortfolioMongoDB start= auto` if it isn't.
5. `MONGODB_URI` in `.env.local` stays the same (`mongodb://127.0.0.1:27017/portfolio`) — it's still listening on the same port, just started by Windows instead of manually.
6. To remove it later: from an elevated prompt, `net stop PortfolioMongoDB` then `mongod.exe --remove --serviceName "PortfolioMongoDB"`.

Both methods write to the same `mongodb-data\` folder, so you can switch between manual-start and service-mode without losing data — just don't run both at once (they'd fight over the same port/files).

### All platforms

- **Environment variables** (`.env.local`, gitignored, never committed per `gaurdrail.md` §6): copy `.env.local.example` to `.env.local`, fill in `MONGODB_URI`, `NEXTAUTH_SECRET` (generate with `openssl rand -base64 32`, or any 32+ byte random string if `openssl` isn't on the PATH on Windows), `NEXTAUTH_URL`.
- **Install dependencies**: `npm install`.
- **Seeding**: `npm run seed:admin` — prompts for the admin email/password interactively and creates the single `AdminUser` document (bcrypt-hashed, never plaintext).
- **Running the app**: `npm run dev` — no deployment step exists yet; "done" for this phase means it runs correctly on `localhost`.
